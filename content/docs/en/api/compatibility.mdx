The control plane exposes **compatibility entry points** for Eureka, Nacos, and Apollo through separate apiserver plugins so legacy clients can migrate onto a unified control plane. This page covers ports and product boundaries. Full third-party protocol semantics remain in each ecosystem’s official docs; the control-plane implementation may cover only common register/discover/config subsets.

## Ports and plugins

| Plugin | Default port | Compatibility target | Config notes |
| --- | ---: | --- | --- |
| `service-eureka` | 8761 | Eureka discovery | Default namespace, delta refresh, unhealthy expiry |
| `service-nacos` | 8848 | Nacos-style discovery/config | Enabled per plugin |
| `service-apollo` | 8890 | Apollo-style config | Enabled per plugin |

Authoritative config: `deploy/conf/pole-apiserver.yaml`. Ports do not listen when the plugin is disabled.

## Product boundaries

1. **Unified control plane**: compatibility adapters enter the same service / config / auth domain model—not a parallel store.
2. **Not a full reimplementation**: do not assume every Nacos / Apollo / Eureka management API or console feature exists.
3. **Coexist with native entries**: prefer [gRPC](/en/docs/api/grpc) or [HTTP OpenAPI](/en/docs/api/http-openapi) for new work; use compatibility ports for migration windows and legacy clients.
4. **Authorization**: protocol adapters extract identity, then share auth interceptors. See [Authorization and resources](/en/docs/principles/auth-protocols).

## When to use

| Scenario | Guidance |
| --- | --- |
| Existing Eureka / Nacos / Apollo clients that cannot change SDKs soon | Enable the matching plugin; verify register and pull |
| New services or clients you can change | Use native gRPC / HTTP; avoid long-term dependence on compatibility |
| Fine-grained Console governance and progressive delivery | Operate on the control-plane resource model; let compatibility clients consume the resulting views |
