Console 是控制面资源的可视化管理层，不是另一套系统。所有变更仍经过鉴权、参数校验与存储；配置和治理规则只有发布后才会进入客户端可见的 active 视图。

![console operation flow](/diagrams/console-operation-flow.svg)

## 登录与初始化

1. 打开 Console：本地默认 `http://127.0.0.1:8080`。
2. 首次部署若提示无主账号，进入 `/init-admin` 创建主账号。
3. 使用主账号登录。后续可在「认证 / 权限」中创建普通用户、用户组、角色与策略。

不要假设存在仓库硬编码的默认密码。`mainUser: pole` 只是配置中的期望主账号名标签。

## 推荐第一次操作路径

按这个顺序建立最小可用环境：

1. **确认 Namespace**  
   预置通常包含 `default` 与 `pole-system`。业务建议单独创建 `dev` / `staging` / `prod` 这类运行环境，不要把 Namespace 当成团队空间。
2. **注册一个服务**  
   在服务清单中创建 Service，再注册或同步 Instance（SDK 注册、Controller 同步或手工录入，取决于接入方式）。
3. **发布一份配置**  
   创建配置分组与文件 → 编辑内容 → 发布版本 → 用客户端监听验证。
4. **发布一条治理规则**  
   在治理工作台创建规则 → Publish → 确认 active release → 用 SDK/Sidecar 验证路由或限流行为。
5. **核对权限**  
   给非管理员账号收敛到具体资源与操作点，避免所有人共用主账号。

## 服务管理

| 操作 | 说明 |
| --- | --- |
| 查看服务列表 | 按 Namespace 过滤服务、健康实例数与基本元数据。 |
| 管理实例 | 查看地址、权重、隔离、心跳与健康状态。 |
| 主动健康检查 | 为需要主动探测的服务配置检查策略。 |
| 服务契约 | 维护调用方需要理解的接口契约信息。 |

实践建议：先保证发现链路稳定，再叠加路由与限流；健康失败应优先表现为摘流，而不是目录混乱。

## 配置中心

![配置分组界面](/images/console/config-groups.png)

典型流程：

1. 创建配置分组。
2. 创建或编辑配置文件（编辑态）。
3. 发布生成不可变版本。
4. 需要时做灰度：先限定客户端范围，再全量或回滚。
5. 客户端通过长轮询或 SSE 感知变更。

约束：

- 单配置内容最大 20,000 字符。
- 列表分页最大 100。
- Pole Agent 确认后的写操作**只保存草稿**，你仍需在配置中心完成发布。

## 治理工作台

![治理工作台](/images/console/governance.png)

工作台覆盖九类能力：路由、泳道、限流、熔断、故障探测、无损上下线、调用鉴权、流量镜像、流量 Mock。

统一操作模型：

1. 创建/编辑规则本体（Console 视图）。
2. 发布 `Rule Release`。
3. 控制系统把目标版本标为 active，旧版本 inactive。
4. 客户端只读 active 视图。
5. 需要时回滚或停止灰度，并保留历史。

![治理规则详情](/images/console/governance-detail.png)

发布前控制面会做权限点检查与资源存在性校验。资源不存在或无权发布时，发布会被拒绝。阅读截图时关注作用域与版本结构；示例规则名不代表生产数据。

详见 [治理规则与灰度发布](/docs/principles/governance-release) 与 [灰度发布实践](/docs/practices/gray-release)。

## 权限管理

| 对象 | 作用 |
| --- | --- |
| 用户 / 用户组 | 认证主体与分组。 |
| 角色 | 绑定一组权限点。 |
| 策略 | 把主体、操作和资源范围关联起来。 |
| 资源映射 | 保证策略引用的服务、配置、规则真实存在。 |

内置受保护角色不可随意破坏。生产环境应关闭“所有人可写”的临时调试策略。

## AI Registry 与 Pole Agent

**MCP Registry**  
管理 MCP Server、Tool 与后端绑定，使 Agent 能发现可用工具。

![MCP Registry](/images/console/mcp-registry.png)

**A2A Registry**  
管理 Agent Card、技能与协议接口元数据。它不负责任务执行或 Agent Runtime。

![A2A Registry](/images/console/a2a-registry.png)

**Pole Agent（`/agent`）**

1. 用自然语言或引导问题查询控制面资源。
2. 对配置变更生成预览差异。
3. 人工确认后写入草稿。
4. 回到配置中心由人发布。

Agent 未配置 LLM Gateway / API key 时，该入口不可用，但不影响其余 Console 功能。

## 系统配置与平台监控

![系统配置](/images/console/system-config.png)

系统配置页展示 Server / Console 登记的类型化配置目录（共 63 项，其中部分可在页面管理）。每个字段会标明：

| Apply mode | 含义 |
| --- | --- |
| BootstrapOnly | 只能改部署配置 |
| RestartRequired | 可发布期望值，实例回报待重启 |
| HotReload | 受控热更新（仅安全 applier 覆盖的领域） |

![平台监控](/images/console/platform-metrics.png)

平台监控页查询 OTel → Collector → GreptimeDB 的控制面概览。没有观测栈时，页面可能无数据，这不代表控制面主链路失败。排障分层见 [观测链路](/docs/principles/observability-chain)。

## 使用原则

- 管理态编辑与运行态发布分开处理。
- 灰度、回滚、停止灰度都要留下可审计历史。
- 业务运行时通过 SDK、Controller、Sidecar 或协议入口消费结果，不要让应用直连管理态表。
- 不把 Namespace 当成多租户隔离方案。
- 不把 A2A Registry 描述成自动执行引擎。
