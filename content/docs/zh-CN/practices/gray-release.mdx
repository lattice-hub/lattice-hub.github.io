---
title: 灰度发布
description: 配置与治理规则从编辑、校验、灰度到全量或回滚的完整实践流程。
---

灰度发布的核心不是“多一个开关”，而是把编辑态与生效态分开：规则或配置先完成编辑与校验，再通过不可变版本进入客户端可见的 active 视图。

![gray release practice](/diagrams/gray-release-practice.svg)

## 适用对象

| 对象 | 发布单元 | 客户端读取 |
| --- | --- | --- |
| 配置中心 | Config File Release | 长轮询 / SSE 拿到的发布版本 |
| 治理规则 | Rule Release | active release 缓存视图 |

服务实例、MCP Server、A2A Agent 走注册发现与 revision，不套用同一套“草稿 → active release”生命周期。

## 标准流程

1. **编辑草稿**  
   在 Console 修改配置内容或规则本体。此时运行时行为不变。
2. **发布前校验**  
   控制面执行鉴权、参数校验、资源存在性检查。缺少目标服务、无权发布或参数非法时直接失败。
3. **选择发布范围**  
   全量或灰度。灰度应先定义客户端标签、百分比或环境范围，再观察。
4. **观察**  
   关注客户端是否拉到新版本、业务错误率、限流/熔断是否按预期触发，以及 History 是否记录操作。
5. **全量或回滚**  
   确认后全量生效；异常则回滚到上一 active 版本，或停止灰度。

## 配置中心实践

配置中心支持**多灰度版本并存**：同一文件可有多条 active gray（按 releaseName 区分），全量发布不会自动结束它们；停灰度按单条操作。客户端同时命中多条灰度时，控制面按 version / mtime 选择最新一条。详见 [配置中心操作](/docs/guides/console/configuration)。

- 先为不同客户端标签集合发布独立灰度，再观察订阅命中。
- 验证通过后「提交为正式草稿」再全量；其它灰度可继续保留或单独停止。
- 保留历史版本，回滚时让客户端能明确识别版本变化。
- 单文件不超过 20,000 字符；超大配置应拆分。
- Pole Agent 只帮助生成草稿，发布按钮仍由人点击。

## 治理规则实践

九类规则共用发布模型，但验证方式不同：

| 规则类型 | 灰度时重点观察 |
| --- | --- |
| 路由 / 泳道 | 流量是否打到预期实例集合与标签 |
| 限流 | 被限请求是否符合阈值，是否误伤 |
| 熔断 / 故障探测 | 打开与恢复是否符合错误率/探测条件 |
| 无损上下线 | 上线延迟、摘流与 readiness 是否平滑 |
| 调用鉴权 | 拒绝是否准确，是否出现越权放行 |
| 镜像 / Mock | 镜像副本与 Mock 短路是否只影响目标范围 |

发布权限点按资源拆分（如 `PublishRouteRules`、`PublishRateLimitRules` 等）。给操作者最小化权限，而不是共享主账号。

## 检查清单

- [ ] Namespace 选对，不是误发到生产环境
- [ ] 目标服务 / 配置 / 规则存在且 revision 可追踪
- [ ] 发布人具备对应 Publish 权限
- [ ] 灰度范围可解释、可收回
- [ ] 回滚路径已确认（上一版本仍在）
- [ ] History / 平台监控可看到本次变更

## 反模式

- 直接改库或绕过 Console/API 写入“生效数据”。
- 把未发布草稿当成客户端已生效配置。
- 无观察窗口的一次性全量发布。
- 用 Pole Agent 自动发布或删除资源。
