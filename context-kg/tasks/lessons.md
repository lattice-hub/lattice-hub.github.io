# 经验记录

## 官网视觉不要过度 AI 化

- 用户纠正：Lattice Hub 官网首版视觉“有点过于 AI 化”，需要重新审视风格。
- 后续规则：服务治理/基础设施类官网应优先呈现可信、克制、工程化的信息架构；AI Native、MCP、Agent 可发现性可以作为差异化能力出现，但不应主导首屏视觉、标题和整体氛围。
- 设计落实：减少发光网格、节点网络、AI 口号和营销式表达；改用清晰架构图、组件关系、事实指标和文档入口来建立可信度。

## 官网实现必须逐条贴合 PRD

- 用户纠正：首页和 PRD 的差别很大，说明实现不能只抓“信息架构方向”，还要逐条核对视觉、交互和验收约束。
- 后续规则：接到 Open Design/PRD 交接稿时，先列出必须落地的硬约束，再实现；完成前按 PRD 验收项逐项自检，尤其关注主色、首屏结构、右侧产品展示形态、分流入口数量和轮播交互细节。
- 设计落实：Pole.IO 首页应使用冷蓝 light canvas，右侧治理拓扑保持开放画布，不把治理图再包进厚重卡片；docs 分流必须覆盖概览、principles、components、blog、reports 五个入口。

## 有截图时优先 1:1 复刻

- 用户纠正：首页效果仍差很多，要求按截图 1:1 复刻。
- 后续规则：当用户提供截图并要求复刻时，截图优先级高于文字总结和自主审美；必须按截图测量首屏比例、导航位置、字体尺度、留白、按钮、箭头、分页器和视觉图形，不再额外发挥。
- 设计落实：先把首屏默认状态做成截图中的 Agent Discovery 页面，再保留必要的链接和轮播交互。

## 官网顶栏保持轻量

- 用户纠正：顶部导航整体高度仍偏高，且“阅读文档”不需要做成按钮，本身应是超链。
- 后续规则：复刻截图时不能把所有右侧入口都强化成 CTA；只有首屏主行动适合按钮化，Header 内的文档入口应优先保持普通链接形态，顶栏高度要服务首屏视觉预算。
- 设计落实：桌面 Header 控制在 60px 左右，移动端控制在 56px 左右；文档入口不使用背景、圆角、阴影和额外 padding。

## 品牌资产优先使用用户提供版本

- 用户纠正：品牌 logo 已提供真实图片，不应继续使用临时手绘 SVG 或重画图形。
- 后续规则：当用户提供品牌资产时，立即替换占位/自绘资产；如果资产带白底但用于玻璃或透明容器，应生成透明背景版再引用。
- 设计落实：导航 glyph 使用 `public/lattice-hub-logo.png`，来源为用户提供的 Lattice Hub logo。

## 第三方品牌入口必须用准确图标

- 用户纠正：顶部 GitHub 入口左侧不应使用 `GitFork` 分叉图标，应使用 GitHub mark。
- 后续规则：第三方品牌入口不能用语义相近的通用图标替代；图标库缺失时，使用准确的品牌 mark SVG，而不是退而使用 lucide 近似图标。
- 设计落实：`SiteHeader` 内 GitHub 入口使用 `GitHubMark` SVG 组件。

## GitHub Pages 404 要核对部署模式

- 用户纠正：Pages 预览页面报 404，说明不能只以 workflow success 或 Pages status=built 作为上线完成。
- 后续规则：GitHub Pages 从 legacy source 切换到 Actions workflow 时，必须确认 `build_type=workflow` 后重新触发一次部署，并用公网 URL 的 HTTP 状态码验证首页、子路径和关键静态资源。
- 设计落实：`lattice-hub/lattice-hub.github.io` 已切换为 workflow 部署；重新跑 `deploy-pages.yml` 后验证 `/`、`/docs/`、`/lattice-hub-logo.png` 均返回 200。

## 文档首页应先讲产品能力

- 用户纠正：`/docs` 首页不应只是 fumadocs 目录组织说明，而应是产品能力的完整介绍页面。
- 后续规则：文档模块首页承担“产品能力总览”职责，先解释 Lattice Hub 解决什么问题、有哪些能力域、组件如何协作、典型数据流是什么，再给阅读路径；目录结构只能作为辅助信息出现。
- 设计落实：`content/docs/index.mdx` 标题使用“产品能力总览”，正文覆盖服务发现、治理规则、配置中心、权限审计、AI Registry、观测链路和多运行时接入。

## 文档架构图必须控制阅读密度

- 用户纠正：Mermaid 默认生成的架构图过大，单个节点占据过多屏幕空间，需要用 `fireworks-tech-graph` 重画，并整体检查所有架构图。
- 后续规则：文档里的架构图、数据流图和流程图应优先使用固定尺寸 SVG 资产，节点标签保持短句，正文承载细节说明；不要把 Mermaid 自动布局直接交给页面渲染，尤其不要让纵向流程图在文档页里无限拉长。
- 设计落实：图资产放在 `public/diagrams`，同名导出 PNG 作为自检产物；MDX 直接引用 SVG，页面只负责响应式缩放。

## MDX 图片不能假设 src 是字符串

- 用户纠正：`/docs` 页面截图显示 `product capability map` 破图，说明文档图片即使在本地构建通过，也可能在导出 HTML 中变成无效 `src`。
- 后续规则：Fumadocs/MDX 静态图片可能被编译为结构化对象；渲染原生 `img` 前必须解包 `.src`，并在完成前检查导出 HTML 与线上 HTML 不再包含 `src="[object Object]"`。
- 设计落实：`src/mdx-components.tsx` 统一处理 MDX 图片 `src`，docs 页面显式使用该组件映射，测试覆盖字符串路径和结构化 `{ src }` 输入。

## Fumadocs 主题变量不能被官网样式污染

- 用户纠正：Fumadocs 文档 light/dark 模式文字显示有问题，且文档格式和 Fumadocs 默认质感差距明显。
- 后续规则：首页视觉 token 只能作用在首页容器内，不能在 `:root` 覆盖 Fumadocs 使用的 `--radius-*`、背景、前景等全局变量；文档图片、表格和 prose 样式不要用裸 `article` 选择器全站覆盖。
- 设计落实：把 Lattice Hub 首页变量收敛到 `.site-shell`，`body` 使用 `--color-fd-background / --color-fd-foreground`，图片补充只限定在 `#nd-docs-layout` 内。

## 文档分区切换应使用 Fumadocs 原生 tabs

- 用户纠正：文档、博客、报告不应该只是左侧目录树里的普通目录，而应该像 Fumadocs 官方示例一样在搜索框下方的分区选择器里切换。
- 后续规则：多内容分区优先接入 `DocsLayout` 的 `tabs` / sidebar dropdown；当前分区下方只展示该分区的目录树，避免把 blog/reports 混进 docs 普通目录。
- 设计落实：`src/lib/docs-navigation.tsx` 维护「文档 / 博客 / 报告」tabs，并按当前 slug 过滤 `source.pageTree`。

## 文档目录应按产品阅读路径组织

- 用户纠正：文档页面左侧目录应参考“是什么 / 使用指南 / 最佳实践”的产品文档结构，而不是只按 Principles、Components、Blog、Reports 这类实现模块堆叠。
- 后续规则：文档分区内优先按用户任务和阅读路径组织目录；技术模块可以作为落地页存在，但侧栏标题要用“简介、功能特性、接入方式、服务端安装、控制台使用、灰度发布”等可理解的产品语言。
- 设计落实：文档分区使用虚拟目录树重组为「Lattice Hub 是什么 / 使用指南 / 最佳实践 / 原理细节」，博客和报告继续通过 Fumadocs tabs 独立切换。

## 首页能力介绍优先使用功能架构图

- 用户纠正：首页 “同一个控制面” 这一段不应只是横向卡片列表，应参考控制面覆盖数据面与业务服务的功能架构图。
- 后续规则：当首页解释控制面能力时，优先用“控制面能力域 + 运行时接入 + 业务服务”的结构关系表达；卡片只能作为局部能力域，不应替代架构图。
- 设计落实：Two operating lines 区块应呈现 Lattice Hub 控制面承载服务管理、流量治理、故障容错、配置治理，并向 SDK、Sidecar、K8s Controller 和业务服务下发治理能力。

## 首页架构图不能照搬参考图

- 用户纠正：首页功能架构图不能直接照搬 image-2 的盒子结构，需要先充分理解项目能力和工作架构，再生成适合 Lattice Hub 的图。
- 后续规则：参考图只用于理解“用架构图替代卡片”的表达方式；最终图必须基于真实能力抽象，包括多协议入口、领域 Server、缓存/事件读模型、Store、K8s Controller、SDK/Sidecar 和 MCP/A2A Registry。
- 设计落实：首页应使用独立生成的工作架构 SVG/PNG，而不是把参考图中的服务 A/B/C、蓝色模块和布局关系直接搬入页面。

## 首页运行时主线是 proxy mesh 与轻量客户端

- 用户纠正：Lattice Hub 整体风格是 proxy mesh，或者客户端一层轻薄的 SDK + proxy，而不是把业务服务盒子作为视觉中心。
- 后续规则：首页架构图右侧应表达“控制面产出治理视图，客户端薄 SDK 订阅视图，local proxy / sidecar / proxy mesh 执行治理”的运行时结构；Agent 能力目录可以作为附加消费面，但不能替代 proxy/mesh 主线。
- 设计落实：运行时消费面优先使用 Thin SDK、Local Proxy/Sidecar、Proxy Mesh/Gateway 等节点表达，避免服务 A/B/C 或业务逻辑盒子。

## 一级导航必须对应独立信息页面

- 用户纠正：首页顶栏的「产品 / 治理 / Pole Agent」不应该只是首页区块的快捷锚点，每个一级入口都应有自己的独立页面。
- 后续规则：站点顶栏出现的一级产品概念默认必须对应稳定路由与完整信息架构；首页锚点只能作为页面内辅助跳转，不能伪装成一级栏目。
- 设计落实：为产品、治理、Pole Agent 分别提供 `/product`、`/governance`、`/agent` 页面，并让桌面导航、移动抽屉、页脚和测试统一指向这些路由。

## 一级导航按用户心智分层，不按功能数量平铺

- 用户纠正：服务治理与 Pole Agent 都属于产品能力，不应与「产品」并列成为一级导航；顶栏只需要「产品 / 组件 / 文档 / 体验」。
- 后续规则：拥有独立页面不等于必须占据一级导航。一级栏目按用户任务与心智模型收敛；专题能力可保留稳定深链，但应由父级产品页承接入口。明确属于动作型的导航项（例如暂未开放的「体验」）可以使用可访问的即时提示，不必为了形式一致创建空页面。
- 设计落实：治理与 Agent 保留深度页面但归入产品体系；产品页提供对等专题入口，顶部仅保留产品、组件、文档和体验动作。

## “动态架构图”必须先确认空间语言

- 用户纠正：首页需要的是参考图式的等距空间架构拓扑，而不是横向阶段流程说明图。
- 后续规则：用户提出“架构数据动态图”时，不能默认把架构事实排成时间轴；必须先区分「流程图」「拓扑图」「部署图」「数据流图」四种表达。若用户给出参考图，优先复刻其空间语言、节点关系、连线方式和运动主体。
- 设计落实：首页 Hero 使用等距俯视拓扑：多协议入口汇入控制平面，配置与治理经过版本门禁形成 Active View，再由 Thin SDK、Sidecar 与 Proxy Mesh 消费；数据包沿连接路径移动，节点收到数据后抬升与点亮。

## 官网架构表达必须先固定抽象层级

- 用户纠正：等距拓扑虽然更接近参考图风格，但把控制面内部领域、发布链和运行时节点全部塞入首屏后，图示仍然混乱，也偏离了“组织组件如何协作”的官网目标。
- 后续规则：首页架构图的一级节点只能是用户能独立理解和选择的组织组件；存储、缓存、事件、内部领域服务和具体版本机制属于仓库或文档内部原理，不得进入首页主图。
- 设计落实：首页只用两个主题分别说明“各组件如何连接控制面”和“治理策略如何抵达执行组件并作用于服务流量”；完整组件职责、控制面/数据面边界和接入方式移到独立架构页。

## 内容抽象层级与视觉语言必须分别处理

- 用户纠正：收敛到组织组件维度是内容层级调整，不代表可以把已经确认的 3D 等距拓扑改成普通平面流程图。
- 后续规则：用户确认参考图后，应建立两条独立约束——“画什么”由信息抽象层级决定，“怎么画”由参考图视觉语言决定；优化其中一条不得擅自覆盖另一条。
- 设计落实：继续使用“组件协作 / 治理生效”两帧低密度内容，但组件必须呈现为等距立体节点、空间基座与沿拓扑路径运动的数据单元。

## 3D 架构图必须服从可读性与页面空间

- 用户纠正：恢复 3D 形式后，若继续使用小节点、斜排区域标题、密集虚线边界和卡片套卡片，仍然会造成图示混乱；3D 本身不是完成标准。
- 后续规则：官网架构图先保证标签水平、字号足够、连线不穿文字、分区一眼可辨，再增加轻量高度和阴影。3D 只能强化层级，不能占用标签与路径的阅读空间。
- 设计落实：首页架构区优先采用无外层卡片的全宽沉浸式场景；参考全景图用大区域和少量基座组织组件，取消斜排说明文字与装饰性虚线领地。

## 治理生效必须落到多语言服务调用

- 用户纠正：首页轮播应把「治理生效」放在第一位；治理图不能只是 SDK、Sidecar、Envoy 等运行时名词的排列，而要回答多语言服务之间发生调用时治理能力怎样真正生效。
- 后续规则：治理叙事必须同时画出两条语义不同的路径——Control Plane 下发的治理视图，以及服务之间的业务调用；两者使用不同线型、颜色与图例，且不能相互遮挡或混淆。
- 设计落实：用 Java、Rust、Go、Python 服务组成调用链，在服务节点上标明 SDK、Sidecar 或 Envoy 等执行点；控制面只表达统一发布与治理视图分发，不下钻内部实现。

## AI Agent 治理要同时表达流量、配置与 Secret 边界

- 用户纠正：通用多语言服务链仍不够贴近当前产品机会；治理生效可以使用 AI Agent 服务，展示 A/B 路由、限流、降级、镜像、Mock、动态 Prompt 与凭据托管。
- 后续规则：AI Agent 场景至少区分三种语义——请求流量、控制面治理视图、配置与 Secret；Prompt 可以进入 Agent 运行时上下文，凭据只能由受控运行时解析并注入 Provider Adapter，不能进入浏览器、日志或模型上下文。
- 设计落实：首帧用示例性的 Agent Gateway 调用拓扑承载流量治理，并把 Dynamic Prompt 与 Pole Secret 放在独立安全边界中；已实现能力与示例拓扑必须分别标注。

## 方向确认后的精修不能继续增加信息

- 用户反馈：AI Agent 治理方向已经正确，下一步需要继续打磨细节和布局。
- 后续规则：当用户认可整体方向后，精修应集中在比例、对齐、留白、连线避让、字号与动效节奏；不要借“打磨”继续增加节点、标签、颜色或新叙事。
- 设计落实：首页治理图维持既定能力与事实边界，优先减少同屏竞争、统一空间网格，让请求主链成为第一视觉焦点。

## 持续动画、品牌命名与双语必须共用一套状态

- 用户纠正：首页架构数据动画不能在首轮播放后停止；组件名称不能混用 `Sidecar`、`Pingora Sidecar`，产品组件统一称为 `Pole Sidecar`；文档和架构图都必须支持中英文。
- 后续规则：承载“系统持续运行”语义的数据流动画应循环播放，并只在 `prefers-reduced-motion` 下静态降级；品牌组件名统一由共享术语表提供，不能散落硬编码；图形结构只维护一份，所有可见标签、图例、说明与无障碍文本均由 locale 字典驱动。
- 设计落实：保留中文现有 URL，新增 `/en/...` 英文镜像路由；文档两种语言使用相同 slug；架构图通过页面 locale 切换 copy，数据包采用错峰无限循环而非一次性播放。

## 蓝绿版本不能画成两个独立服务

- 用户纠正：Agent Gateway 路由的 A/B 不是两个不同 Agent 服务，而是同一个服务的蓝绿版本；GW 还承担千人千面的限流与比例分流，版本到 Provider Adapter 的调用需要表达服务身份鉴权。
- 后续规则：流量治理图必须区分「逻辑服务」与「部署版本」。蓝绿节点共享同一个服务名，只用版本色、版本标签和比例区分；限流执行点写在 Gateway；身份鉴权标注贴近服务到下游适配器的调用边，不与平台凭据托管混为一谈。
- 设计落实：Gateway 到蓝/绿版本的两条分支分别显示示例比例，版本汇聚到 Provider Adapter 前增加服务身份鉴权语义；中英文、桌面与移动使用同一组字段。

## 治理能力不能只靠文字标签表达

- 用户纠正：把限流、蓝绿、熔断、镜像、Mock、Prompt 与 Secret 写在节点或横条上，并不能让用户理解这些治理能力带来的实际收益。
- 后续规则：官网治理动态图必须使用「触发条件 → 路径变化 → 可见结果 → 用户收益」的完整场景表达。能力名称只做索引，主要信息要由流量被拦截、按比例分流、故障切换、镜像复制、Mock 截断、Prompt 版本切换和 Secret 在边界内解封等状态变化承担。
- 设计落实：用一个持续循环的请求旅程串联治理场景；每个阶段只聚焦一项关键能力，并在结果节点显示可验证的收益状态，避免继续增加静态说明条。

## 定向灰度应画成用户泳道，而不是只画比例

- 用户纠正：治理图应采用上下分层；请求侧需要明确展示 A、B 两类用户，其中 A 用户进入 BLUE 稳定版本，B 用户进入 GREEN 体验版本，而不是只有一个通用请求节点和抽象的 80/20 点阵。
- 后续规则：当场景强调“谁获得什么体验”时，优先用用户分组泳道表达路由结果；流量比例只能作为次级发布参数，不能替代用户、路由条件和版本体验之间的对应关系。BLUE / GREEN 必须继续属于同一个逻辑 Agent Service。
- 设计落实：管理控制面置于上层，请求执行面置于下层；下层用两条不交叉的请求路径分别连接 User A 与稳定版本、User B 与体验版本，并通过共享 Gateway、身份鉴权和 Provider Adapter 保留完整治理链路。
